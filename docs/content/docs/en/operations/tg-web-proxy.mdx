We1ssBoard can install and manage
[tproxy-server](https://github.com/telegramdesktop/tproxy-server), the relay
that lets Telegram clients reach MTProxy over ordinary HTTPS or WebSocket
traffic. Open **Telegram WEB Proxy** in the sidebar (`/panel/tg-web-proxy`).

<Callout type="warn">
  Management needs a Linux host with systemd. On other hosts the page is
  read-only. The upstream installer supports Ubuntu/Debian x86_64 and takes over
  ports **80** and **443** with Caddy, so don't run it on a host where another
  web server or an Xray inbound already listens on those ports.
</Callout>

## How it fits together

| Unit              | Role                                                         |
| ----------------- | ------------------------------------------------------------ |
| `caddy`           | Public TLS on 443, forwards the proxy path to the relay      |
| `tproxy-server`   | The relay, listening on `127.0.0.1:8080` only                |
| `mtproxy`         | MTProxy backends the relay forwards each profile to          |
| `tproxy-firewall` | Firewall rules that keep the loopback ports closed to others |

The relay's admin listener (`127.0.0.1:8081` by default) exposes `/healthz`,
`/readyz` and `/metrics`. We1ssBoard reads it **server-side only** and shows the
result on the Overview tab; it is never published.

## Install

<Steps>

<Step>
### Prepare DNS

Point an A/AAAA record for the proxy hostname (for example `tg.example.com`) at
the server, and make sure ports 80 and 443 are free and reachable.
</Step>

<Step>
### Run the installer

On the **Overview** tab click **Install** and fill in the hostname, the ACME
email, the first profile's secret (generate one in the form), and optionally a
base path, a site to serve on the root (`--site-dir` or `--site-upstream`) and
the number of MTProxy workers.

We1ssBoard downloads the latest upstream source to `/usr/local/src/tproxy-server`
and runs `deploy/install.sh` as a transient systemd unit, so it survives a panel
restart. The secret is passed on stdin from a `0400` file that is deleted
afterwards; it never appears in a process list. The job log streams on the
Overview tab.
</Step>

<Step>
### Verify

When the job succeeds the units table should show every unit as active and the
admin probe as healthy and ready.
</Step>

</Steps>

**Update relay** re-downloads the upstream source and runs `deploy/update-relay.sh`.

### Adopting an existing install

If tproxy-server was installed by hand with the stock layout
(`/etc/tproxy-server/config.json`, `/etc/tproxy-server/profiles.json`,
`/usr/local/bin/tproxy-server`), We1ssBoard picks it up automatically: no
re-install is needed. Unknown keys in `config.json` are preserved on save.

## Profiles

Each profile is one entry in `profiles.json`:

- **Name**: unique, up to 64 characters.
- **Secret**: 32 hex characters (or `dd` + 32 hex). Secrets must be unique.
- **Backend**: a loopback `host:port` of an MTProxy instance, such as
  `127.0.0.1:8443`.
- **Carrier mode** (optional): `https`, `https-lanes`, `websocket` or
  `websocket-lanes`. This is **server-side only** — share links stay
  `server` + `secret`; the client learns the mode after `POST /api/v1/session`.
  Prefer `websocket` over `websocket-lanes` on macOS Desktop.
- **Limits** (optional): per-profile caps, which can't exceed the global limits.

<Callout type="info">
  The relay only forwards opaque obfuscated2 traffic, so each backend must be an
  official MTProxy that knows the profile's secret (mtg cannot serve it: it only
  takes FakeTLS secrets). `127.0.0.1:2398` is the installer's `mtproxy.service`.
  For every other backend port We1ssBoard runs an official MTProxy itself
  (transient `we1ssboard-mtproxy-<port>` units, up to 16 secrets per port) and
  firewalls the port to loopback. Their state is on the Overview tab.
</Callout>

### WebSocket carrier and stock Caddy

Stock Caddy installs often enable `encode`. That stalls the bridge's
`GET /api/v1/ws` (classic Upgrade) and HTTP/2 `CONNECT` upgrades (see
[caddyserver/caddy#6733](https://github.com/caddyserver/caddy/issues/6733));
HTTPS long-poll still works. As soon as a profile uses a websocket carrier,
We1ssBoard patches `/etc/caddy/Caddyfile` to **disable `encode`** on the site
block, validating it with `caddy validate` under `caddy.service`'s environment
first. **Fix Caddy for WebSocket** on the Overview tab re-applies it, e.g. after
an upstream update rewrote the Caddyfile.

## Share links

Click **Share** on a profile to get the link, a `tg://` deep link and a QR code.
For a root deployment the link is
`https://t.me/webproxy?server=<hostname>&secret=<hex>`. With a base path the
server becomes `<hostname>/<base>` and the secret is encoded the way Telegram
expects for path deployments; We1ssBoard handles this for you.

## Client bindings

Bind a client to a profile so its **raw** subscription and the client **QR code**
menu carry a web-proxy link next to inbound links. Open the client's form, go to
the **Telegram WEB Proxy** tab and pick a profile, or bind many clients at once
on the **Users** tab (below). JSON and Clash subscriptions never include the
link.

- **Shared binding.** The client advertises the chosen profile's own secret.
  Everyone bound to that profile shares one secret.
- **Dedicated secret.** We1ssBoard creates a profile named `fb:<email>`, cloned
  from the chosen one (carrier mode, limits) with a fresh random secret on a
  panel-run MTProxy port. A disabled client keeps its profile (and link) but is
  parked on a port nothing serves until it is enabled again. The profile is written to
  `profiles.json` by a background sync a few seconds after you save. The link
  appears once the sync finishes.
- Disabled clients and clients without a matching relay profile get no link.
- A profile that clients are bound to cannot be deleted or renamed, and `fb:`
  profiles are managed by We1ssBoard: edit them by unbinding the client.
- Deleting a client drops its binding and its `fb:` profile.

Older releases created `fb-tgwp:<email>` mtg inbounds for dedicated secrets; they
never worked with the relay and are removed by the next sync.

### Users tab

**Connections → Telegram WEB Proxy → Users** shows who is bound to which relay,
for this panel and for every node that runs one:

1. Pick the relay at the top. Each one shows how many clients are bound to it.
2. Pick the **profile** to bind to. On this panel's relay you can also choose
   between a shared binding and a dedicated secret; a node's relay always binds
   dedicated.
3. Move clients between **Not bound** and **Bound**: search, select several and
   press **Bind** or **Unbind**. A client bound to another relay is marked
   "now on …"; binding it here moves it.

Under the lists, the bindings table of the selected relay shows each client's
profile, its secret and its link.

## Relay on a node

The relay does not have to run on the panel that sells the subscriptions. A
common setup is a relay on an EU node while clients live on a master panel in
another country. Install the relay on the node, manage its profiles from the
master under **Nodes & hosts → node → Telegram WEB Proxy**, and bind master
clients to it on the **Users** tab by picking the node's relay (or with **Add to
subscriptions** on one of its profiles).

Both panels then keep dedicated `fb:` profiles in the node's `profiles.json`:
the node for its own clients, the master for the clients it binds there. Each
profile records its owner in `dedicated-owners.json` beside `profiles.json`,
and each panel only creates, changes or removes its own profiles. The relay
restarts only when one of them really changes. Profiles created before 1.8.1 are
claimed by whichever panel still binds them, keeping their secrets, so client
links do not change; profiles nobody claims are removed after 15 minutes.

## Status on the dashboard

The **Overview** page (and the overview screen of the mobile app) shows a
**Telegram WEB Proxy** card as soon as this panel runs a relay or binds clients
to one on a node. Each row is one relay host: this panel and every node with a
relay. It shows whether the relay is running and ready, its profiles, bound
clients and MTProxy backends, and the error when something is wrong. A node the
panel cannot reach is listed only when clients are bound to it.

## Route backend via outbound

Same layout as [WEB Panel Proxy](https://gitlab.com/POLESNIESOVETI12/web-panel-proxy)
and stock `tproxy-server`: a **local** MTProxy stays `127.0.0.1:<port>` — the
relay dials it on this host. **Route via outbound** only builds an Xray tunnel
when the backend is a **public** MTProxy address; that tunnel is then sent
through the chosen outbound. Tunneling `127.0.0.1` through a remote outbound
dials the far side's loopback and breaks the relay while an outbound check can
still pass. The MTProxy must accept the profile secret.

## Public site

The **Public site** tab manages a panel-owned landing page under
`/srv/tproxy-site` (`index.html` editor, asset upload, sandbox preview) — the
same path stock tproxy / WEB Panel Proxy installs use so the `tproxy` user can
read the files. The default page is a dark “Anywhere app” signup shell (operator
camouflage); edit or reset it from the panel. Saving activates `public_dir` on
that directory and clears `public_upstream`.

## Config

The **Relay config** tab edits `config.json`: the hostname and base path, the listen
and admin addresses, the public upstream, global limits and timeouts. On a fresh
host with no profiles yet, the form also asks for the first profile, since the
relay refuses to start without one.

## Troubleshooting

**`read-only file system` when saving config, a profile, or Fix Caddy.** The
panel unit uses `ProtectSystem=full`, which makes `/etc` read-only. We1ssBoard
needs `ReadWritePaths=-/etc/tproxy-server -/etc/caddy` and `CAP_CHOWN` (so
tproxy files can be `root:tproxy`). Stock installs from a current release
include both; on an older unit, replace the drop-in below and restart:

```bash
sudo mkdir -p /etc/systemd/system/we1ssboard.service.d
sudo tee /etc/systemd/system/we1ssboard.service.d/20-tproxy.conf >/dev/null <<'EOF'
[Service]
ReadWritePaths=-/etc/tproxy-server -/etc/caddy
# Drop-ins replace CapabilityBoundingSet entirely — keep the full set.
CapabilityBoundingSet=CAP_DAC_OVERRIDE CAP_NET_ADMIN CAP_NET_BIND_SERVICE CAP_NET_RAW CAP_CHOWN
EOF
sudo systemctl daemon-reload
sudo systemctl restart we1ssboard
```

Then save the relay config / profile again, or click **Fix Caddy for WebSocket**.

**`permission denied` opening `config.json` in `tproxy-server` logs.** The panel
wrote the file as `root:root` (no `CAP_CHOWN`). Fix ownership now, then apply
the drop-in above so the next save does not break it again:

```bash
sudo chown -R root:tproxy /etc/tproxy-server
sudo chmod 750 /etc/tproxy-server
sudo chmod 640 /etc/tproxy-server/config.json
sudo chmod 400 /etc/tproxy-server/profiles.json
sudo systemctl restart tproxy-server
```

## Safety guarantees

Every save (config or profile) goes through the same steps:

1. The input is validated. Listeners, the admin address, the public upstream and
   all backends must be numeric loopback addresses.
2. Candidate files are written next to the live ones, with `profiles.json` at
   mode `0400`.
3. `tproxy-server -config … -profiles-file … -check` validates the candidates.
   If it fails, the live files stay untouched and the error is shown.
4. The previous files are kept as `*.we1ssboard-prev`, and the candidates replace
   them.
5. If the relay was running, it is restarted. **Start** and **Restart** also run
   the check first.
