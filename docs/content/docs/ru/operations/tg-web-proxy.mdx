We1ssBoard умеет устанавливать и обслуживать
[tproxy-server](https://github.com/telegramdesktop/tproxy-server) — релей,
через который клиенты Telegram подключаются к MTProxy поверх обычного HTTPS или
WebSocket. Откройте **Telegram WEB Proxy** в боковом меню (`/panel/tg-web-proxy`).

<Callout type="warn">
  Для управления нужен Linux-хост с systemd; на остальных страница доступна
  только для чтения. Установщик поддерживает Ubuntu/Debian x86_64 и занимает
  порты **80** и **443** под Caddy, поэтому не запускайте его там, где эти порты
  уже заняты другим веб-сервером или inbound Xray.
</Callout>

## Как это устроено

| Юнит              | Назначение                                                    |
| ----------------- | ------------------------------------------------------------- |
| `caddy`           | Публичный TLS на 443, проксирует путь прокси на релей         |
| `tproxy-server`   | Релей, слушает только `127.0.0.1:8080`                        |
| `mtproxy`         | Бэкенды MTProxy, на которые релей направляет профили          |
| `tproxy-firewall` | Правила файрвола, закрывающие loopback-порты от внешнего мира |

Админ-листенер релея (по умолчанию `127.0.0.1:8081`) отдаёт `/healthz`,
`/readyz` и `/metrics`. We1ssBoard опрашивает его **только на стороне сервера** и
показывает результат на вкладке «Обзор»; наружу он не публикуется.

## Установка

<Steps>

<Step>
### Подготовьте DNS

Направьте A/AAAA-запись имени прокси (например, `tg.example.com`) на сервер и
убедитесь, что порты 80 и 443 свободны и доступны извне.
</Step>

<Step>
### Запустите установщик

На вкладке «Обзор» нажмите **Установить** и укажите имя хоста, email для ACME,
секрет первого профиля (его можно сгенерировать в форме) и, при необходимости,
базовый путь, сайт для корня (`--site-dir` или `--site-upstream`) и число
воркеров MTProxy.

We1ssBoard скачивает актуальные исходники в `/usr/local/src/tproxy-server` и
запускает `deploy/install.sh` во временном юните systemd, поэтому установка
переживает перезапуск панели. Секрет передаётся через stdin из файла с правами
`0400`, который затем удаляется; в списке процессов он не появляется. Лог задачи
выводится на вкладке «Обзор».
</Step>

<Step>
### Проверьте

После успешного завершения все юниты в таблице должны быть активны, а
админ-проверка — показывать healthy и ready.
</Step>

</Steps>

**Обновить релей** заново скачивает исходники и запускает `deploy/update-relay.sh`.

### Существующая установка

Если tproxy-server установлен вручную со стандартной раскладкой
(`/etc/tproxy-server/config.json`, `/etc/tproxy-server/profiles.json`,
`/usr/local/bin/tproxy-server`), We1ssBoard подхватит его автоматически,
переустанавливать не нужно. Неизвестные ключи в `config.json` при сохранении
сохраняются.

## Профили

Каждый профиль — запись в `profiles.json`:

- **Имя** — уникальное, до 64 символов.
- **Секрет** — 32 hex-символа (или `dd` + 32 hex), без повторов.
- **Бэкенд** — loopback `host:port` экземпляра MTProxy, например
  `127.0.0.1:8443`.
- **Режим транспорта** (необязательно) — `https`, `https-lanes`, `websocket`
  или `websocket-lanes`. Это настройка **только на сервере** — в ссылках
  остаются `server` + `secret`; клиент узнаёт режим после
  `POST /api/v1/session`. На macOS Desktop лучше `websocket`, а не
  `websocket-lanes`.
- **Лимиты** (необязательно) — не могут превышать глобальные.

<Callout type="info">
  Релей пересылает непрозрачный трафик obfuscated2, поэтому бэкенд — это
  официальный MTProxy, знающий секрет профиля (mtg не подходит: он принимает
  только FakeTLS-секреты). `127.0.0.1:2398` — это `mtproxy.service` установщика.
  Для любого другого порта We1ssBoard сам запускает официальный MTProxy
  (временные юниты `we1ssboard-mtproxy-<port>`, до 16 секретов на порт) и
  закрывает порт файрволом снаружи. Их состояние видно на вкладке Overview.
</Callout>

### WebSocket и stock Caddy

В типовой установке Caddy включает `encode`. Это «зависает» на `GET /api/v1/ws`
(обычный Upgrade) и на HTTP/2 `CONNECT`
([caddyserver/caddy#6733](https://github.com/caddyserver/caddy/issues/6733));
HTTPS long-poll при этом работает. Как только у профиля websocket-режим,
We1ssBoard сам отключает `encode` в site-блоке `/etc/caddy/Caddyfile`, заранее
проверив файл `caddy validate` с окружением `caddy.service`. Кнопка
**Исправить Caddy для WebSocket** на вкладке Overview повторяет патч, например
после upstream-обновления, перезаписавшего Caddyfile.

## Ссылки для клиентов

Кнопка **Поделиться** у профиля показывает ссылку, deep link `tg://` и QR-код.
Для установки в корень ссылка выглядит как
`https://t.me/webproxy?server=<hostname>&secret=<hex>`. С базовым путём сервер
становится `<hostname>/<base>`, а секрет кодируется так, как ожидает Telegram;
We1ssBoard делает это сам.

## Привязки клиентов

Привяжите клиента к профилю — ссылка web-proxy появится в **«сырой»** подписке и
в меню **QR-код**. Откройте форму клиента, вкладку **Telegram WEB Proxy**, и
выберите профиль, либо привяжите сразу нескольких на вкладке **Пользователи**
(ниже). В подписках JSON и Clash этой ссылки никогда нет.

- **Общая привязка.** Клиент получает секрет самого выбранного профиля. У всех
  клиентов одного профиля секрет общий.
- **Отдельный секрет.** We1ssBoard создаёт профиль `fb:<email>`, скопированный с
  выбранного (режим carrier, лимиты), с новым случайным секретом на порту
  MTProxy, который запускает панель. Отключённый клиент сохраняет профиль (и
  ссылку), но «паркуется» на порт без сервера, пока его снова не включат. Профиль пишется в
  `profiles.json` фоновой синхронизацией через несколько секунд; ссылка
  появляется после неё.
- У отключённых клиентов и клиентов без профиля на релее ссылки нет.
- Профиль, к которому привязаны клиенты, нельзя удалить или переименовать, а
  профили `fb:` управляются We1ssBoard: чтобы изменить их, отвяжите клиента.
- При удалении клиента удаляются его привязка и профиль `fb:`.

Старые версии создавали для отдельных секретов mtg-инбаунды `fb-tgwp:<email>`;
с релеем они не работали и удаляются при следующей синхронизации.

### Вкладка «Пользователи»

**Подключения → Telegram WEB-прокси → Пользователи** показывает, кто к какому
relay привязан, — для этой панели и для каждого узла, где relay установлен:

1. Выберите relay вверху. Рядом с каждым видно, сколько клиентов к нему привязано.
2. Выберите **профиль** для привязки. На relay этой панели можно выбрать общую
   привязку или отдельный секрет; на relay узла привязка всегда с отдельным
   секретом.
3. Переносите клиентов между списками **Не привязаны** и **Привязаны**: найдите,
   отметьте нескольких и нажмите **Привязать** или **Отвязать**. Клиент,
   привязанный к другому relay, помечен «сейчас на …»; при привязке он переезжает сюда.

Под списками — таблица привязок выбранного relay: профиль, секрет и ссылка
каждого клиента.

## Relay на узле

Relay не обязан работать на той же панели, что выдаёт подписки. Частый вариант:
relay на EU-узле, а клиенты на главной панели в другой стране. Установите relay
на узел, управляйте его профилями с главной панели в **Узлы и хосты → узел →
Telegram WEB-прокси** и привязывайте клиентов главной панели на вкладке
**Пользователи**, выбрав relay узла (или кнопкой **Добавить в подписки** у его профиля).

Тогда в `profiles.json` узла выделенные профили `fb:` держат обе панели: узел
для своих клиентов, главная панель для тех, кого она туда привязала. У каждого
профиля записан владелец в `dedicated-owners.json` рядом с `profiles.json`, и
каждая панель создаёт, меняет и удаляет только свои профили. Relay
перезапускается, только когда один из них действительно изменился. Профили,
созданные до 1.8.1, забирает та панель, которая их ещё привязывает, вместе с
секретами, поэтому ссылки клиентов не меняются. Профили, которые никто не забрал,
удаляются через 15 минут.

## Статус на дашборде

На **Дашборде** (и на главном экране мобильного приложения) появляется карточка
**Telegram WEB-прокси**, как только эта панель запускает relay или привязывает
клиентов к relay на узле. Каждая строка — один сервер с relay: эта панель и
каждый узел. В строке видно, работает ли relay и готов ли он, число профилей,
привязанных клиентов и MTProxy-бэкендов, а при ошибке — её текст. Недоступный
узел показывается, только если к нему привязаны клиенты.

## Маршрутизация backend через outbound

Как в [WEB Panel Proxy](https://gitlab.com/POLESNIESOVETI12/web-panel-proxy) и
stock `tproxy-server`: **локальный** MTProxy остаётся `127.0.0.1:<порт>` — релей
набирает его на этом хосте. **Route via outbound** строит Xray-туннель только
для **публичного** адреса MTProxy и тогда отправляет его через выбранный
outbound. Туннель `127.0.0.1` через удалённый outbound открывает loopback на
дальней стороне и ломает релей, при этом проверка outbound может всё ещё
проходить. MTProxy должен принимать секрет профиля.

## Публичный сайт

Вкладка **Public site** управляет лендингом панели в
`/srv/tproxy-site` (редактор `index.html`, загрузка ассетов, preview в sandbox)
— тот же путь, что у stock tproxy / WEB Panel Proxy, чтобы пользователь
`tproxy` мог читать файлы. Сохранение включает `public_dir` на этот каталог и
очищает `public_upstream`.

## Конфигурация

Вкладка «Конфигурация релея» редактирует `config.json`: имя хоста и базовый путь,
адреса листенера и админки, публичный upstream, глобальные лимиты и таймауты. На
новом хосте без профилей форма также запрашивает первый профиль — без него релей
не запустится.

## Устранение неполадок

**`read-only file system` при сохранении конфига, профиля или Fix Caddy.** Unit
панели использует `ProtectSystem=full`, из‑за чего `/etc` только для чтения.
We1ssBoard нужны `ReadWritePaths=-/etc/tproxy-server -/etc/caddy` и `CAP_CHOWN`
(файлы tproxy — `root:tproxy`). В актуальном релизе это уже есть; на старом
unit замените drop-in и перезапустите:

```bash
sudo mkdir -p /etc/systemd/system/we1ssboard.service.d
sudo tee /etc/systemd/system/we1ssboard.service.d/20-tproxy.conf >/dev/null <<'EOF'
[Service]
ReadWritePaths=-/etc/tproxy-server -/etc/caddy
# Drop-in полностью заменяет CapabilityBoundingSet — нужен полный набор.
CapabilityBoundingSet=CAP_DAC_OVERRIDE CAP_NET_ADMIN CAP_NET_BIND_SERVICE CAP_NET_RAW CAP_CHOWN
EOF
sudo systemctl daemon-reload
sudo systemctl restart we1ssboard
```

После этого снова сохраните конфиг / профиль или нажмите **Исправить Caddy для
WebSocket**.

**`permission denied` на `config.json` в логах `tproxy-server`.** Панель записала
файл как `root:root` (нет `CAP_CHOWN`). Исправьте владельца сейчас и примените
drop-in выше, чтобы следующее сохранение снова не ломало права:

```bash
sudo chown -R root:tproxy /etc/tproxy-server
sudo chmod 750 /etc/tproxy-server
sudo chmod 640 /etc/tproxy-server/config.json
sudo chmod 400 /etc/tproxy-server/profiles.json
sudo systemctl restart tproxy-server
```

## Гарантии безопасности

Любое сохранение (конфигурации или профиля) проходит одни и те же шаги:

1. Проверка ввода: листенеры, админ-адрес, публичный upstream и все бэкенды
   должны быть числовыми loopback-адресами.
2. Кандидаты записываются рядом с рабочими файлами, `profiles.json` — с правами
   `0400`.
3. `tproxy-server -config … -profiles-file … -check` проверяет кандидатов. При
   ошибке рабочие файлы не меняются, а ошибка показывается в интерфейсе.
4. Предыдущие файлы сохраняются как `*.we1ssboard-prev`, затем кандидаты их
   заменяют.
5. Если релей был запущен, он перезапускается. **Запуск** и **Перезапуск** тоже
   сначала выполняют проверку.
