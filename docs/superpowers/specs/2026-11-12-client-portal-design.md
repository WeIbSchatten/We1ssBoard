# Личный кабинет клиента — дизайн

Дата: 2026-11-12. Статус: на ревью.

## 1. Цель

Клиент We1ssBoard получает личный кабинет с входом по логину и паролю:

- видит всё о себе: статус, срок, лимит и расход трафика, свою подписку;
- скрывает из своей подписки ключи (строки `vless://`, `hysteria2://` …), которыми не
  пользуется; в панели доступ к этим подключениям остаётся выданным;
- меняет пароль; первый пароль временный и выдаётся админом;
- входит в We1ssConnect логином и паролем — подписка подтягивается сама, без ссылки.

Критерий готовности: клиент без ссылки на подписку входит в кабинет и в приложение,
а его подписка во всех форматах (raw, JSON, Clash) не содержит скрытых им ключей.

Вне рамок: клиент не меняет ничего серверного (лимиты, сроки, набор выданных
подключений задаёт только админ); вход в клиенте OpenWrt (остаётся ссылка на подписку).

## 2. Ключевые решения

| Вопрос | Решение |
|---|---|
| Где живёт кабинет | На подписочном сервере (`internal/sub`), не на порту панели: админку не надо открывать клиентам |
| Логин | `email` клиента. LDAP-синхронизация уже пишет туда логин из каталога |
| Пароль | Свой пароль кабинета (bcrypt) + вход через LDAP, если он включён в панели |
| Первый пароль | Админ генерирует временный и видит его один раз; при наличии `tgId` пароль уходит и в Telegram-бота |
| Что скрывается | Отдельный ключ = пара `(inbound_id, host_id)`; `host_id = 0` — ключ инбаунда без хостов |
| Последний ключ | Скрыть последний видимый ключ нельзя |
| Сессия приложения | Собственный токен на устройство; смена пароля отзывает все токены |
| Включение | Настройка «Личный кабинет», по умолчанию выключена |

Отвергнутые варианты: кабинет на порту панели (`/me`) — открывает админку всем
клиентам; вход в приложение обменом на ссылку подписки — смена пароля не отзывала бы
доступ приложения.

## 3. Данные

Одна миграция в `internal/database/db.go`.

**`clients`** (`model.ClientRecord`), новые колонки:

- `portal_password_hash` `string` — bcrypt; пусто = своего пароля нет;
- `portal_must_change` `bool` — пароль временный.

**`client_portal_tokens`** (новая модель `ClientPortalToken`):

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | int PK | |
| `client_id` | int, index | `clients.id` |
| `token_hash` | string(64), unique | SHA-256 токена; сам токен не хранится |
| `device_name` | string | присылает приложение |
| `created_at`, `last_used_at` | int64 ms | |

**`client_sub_hidden`** (новая модель `ClientSubHidden`), PK `(client_id, inbound_id, host_id)`.

Очистка `client_sub_hidden`: при удалении клиента, отвязке клиента от инбаунда
(`client_inbounds`), удалении хоста (его `host_id`) и удалении инбаунда. Очистка
`client_portal_tokens`: при удалении клиента.

**Настройка** `portalEnabled` (`SettingService`, по умолчанию `false`) в разделе подписки.

Все таблицы существуют только на главной панели и не синхронизируются с узлами.
Изменения в кабинете не меняют конфиг Xray, поэтому не идут через `runtime.Runtime`.

## 4. Аутентификация

Вход `login` + `password`:

1. Клиент с таким `email` ищется в `clients`. Нет клиента — общий ответ «неверный логин или пароль».
2. Если `portal_password_hash` не пуст — проверяется bcrypt.
3. Иначе, если в панели включён LDAP, — `ldap.AuthenticateUser(cfg, login, password)`.
4. Иначе — отказ.

Ограничение перебора: тот же механизм, что у админа (`internal/web/controller/login_limiter.go`),
выносится в общий пакет и используется с ключом «IP + логин». После превышения — 429 с
`Retry-After`. Неверный логин и неверный пароль дают одинаковый ответ.

Временный пароль (`portal_must_change = true`): после входа разрешены только
`POST /portal/api/password` и `POST /portal/api/logout`; остальные запросы — 403 с кодом
`must_change_password`.

LDAP-клиент (своего хэша нет, вход через каталог) не может менять пароль в кабинете.

Отзыв: смена пароля, выдача нового временного пароля админом, «Отозвать доступ» и
выключение настройки `portalEnabled` удаляют все токены и веб-сессии клиента.

Выключенный или просроченный клиент может войти и видит причину, но только смотрит:
`PUT /portal/api/hidden` и `DELETE /portal/api/devices/:id` отвечают 403 `client_disabled`;
смена пароля и выход разрешены.

**Веб-сессия:** cookie подписочного сервера (`HttpOnly`, `Secure` при HTTPS,
`SameSite=Strict`), отдельный секрет от панели, CSRF-токен на изменяющие запросы.
Сессия хранит `client_id` и версию пароля, чтобы смена пароля обнуляла старые сессии.

**Токен приложения:** 32 случайных байта, base64url. Передаётся в `Authorization: Bearer`.

## 5. API кабинета (подписочный сервер)

Все маршруты возвращают 404, когда `portalEnabled = false`.

| Метод и путь | Назначение |
|---|---|
| `GET /portal` | Страница кабинета (`portal.html`) |
| `POST /portal/api/login` | `{login, password, client: "web"\|"app", device}` → web: cookie; app: `{token}` |
| `POST /portal/api/logout` | Завершить веб-сессию или отозвать текущий токен |
| `POST /portal/api/password` | `{current, new}`, `new` ≥ 8 символов; снимает `portal_must_change`, отзывает остальные сессии и токены |
| `GET /portal/api/me` | Профиль: email, статус, срок, лимит и расход, группа, ссылка подписки, ключи `[{inboundId, hostId, remark, protocol, hidden}]`, устройства, `ldap: bool`, `mustChange: bool` |
| `PUT /portal/api/hidden` | `{keys: [{inboundId, hostId}]}` — заменяет набор; 400, если ключ не принадлежит клиенту или видимых не остаётся |
| `DELETE /portal/api/devices/:id` | Отозвать токен устройства клиента |
| `GET /portal/api/sub?format=raw\|json\|clash` | Подписка по токену, тот же вывод и заголовки (`subscription-userinfo`), что у `/sub/:subid`; обновляет `last_used_at`; 401, если токен отозван |

Список ключей в `/me` строится тем же кодом, что подписка (инбаунды клиента × хосты),
чтобы названия совпадали со строками подписки.

Маршруты подписочного сервера не входят в `TestRouteRegistryContract`; описываются в
документации сайта `docs/`.

## 6. Фильтр подписки

`SubService` после определения клиента загружает его скрытые пары и пропускает их при
генерации: в `service.go` (raw), `json_service.go` (JSON), `clash_service.go` (Clash),
включая разворачивание хостов в `host_sub.go`. Фильтр действует и на `/sub/:subid`, и на
`/portal/api/sub`. Ссылки и QR в панели (`service/client_link.go`) остаются полными.

## 7. Админка и Telegram

**Карточка клиента** — блок «Личный кабинет» (виден при включённой настройке):

- статус: «нет доступа» / «временный пароль» / «свой пароль» / «LDAP»;
- «Выдать временный пароль» — генерирует пароль (12 символов), показывает один раз с
  копированием, ставит `portal_must_change`, отзывает токены; при `tgId` и включённом
  боте отправляет пароль клиенту;
- «Отозвать доступ» — стирает хэш, токены и сессии;
- число скрытых клиентом ключей (только чтение).

Эндпоинты: `POST /panel/api/clients/:id/portal/password`,
`POST /panel/api/clients/:id/portal/revoke`. По правилам CLAUDE.md: запись в
`frontend/src/pages/api-docs/endpoints.ts`, структуры ответа в `StructAllow`
(`tools/openapigen`), `make gen`, копия `openapi.json` в `docs/` и `pnpm gen:api`.

**Telegram-бот** (`service/tgbot/`): клиенту с привязанным `tgId` — действие «Сбросить
пароль кабинета», присылает новый временный пароль.

## 8. Страница кабинета

Новый вход Vite `frontend/portal.html` → `internal/web/dist/portal.html`, Ant Design, та же
тема, что у страницы подписки; переиспользует её компоненты (QR, копирование ссылки).
Строки — ключи перевода во всех 13 файлах `internal/web/translation/`.

Экраны:

1. **Вход** — логин, пароль. Временный пароль → сразу обязательная смена.
2. **Профиль** — статус, срок, полоса трафика, группа, «Скопировать ссылку», QR.
3. **Мои ключи** — «название · протокол» с переключателями; последний видимый
   переключатель неактивен с подсказкой.
4. **Устройства** — имя, последний вход, «Выйти».
5. **Безопасность** — смена пароля; для LDAP — надпись «Пароль управляется каталогом компании».

## 9. We1ssConnect (Android и десктоп)

- На экране «Добавить серверы» — вкладка «Войти по логину»: адрес сервера (база
  подписочного сервера), логин, пароль. `POST /portal/api/login` с `client: "app"` и
  именем устройства.
- Создаётся профиль типа «аккаунт» (`Profile.account = {base, token}`), пароль не хранится.
- Обновление профиля — `GET /portal/api/sub` с токеном. Нативный `Fetch` (Android-модуль
  `xray-vpn` и `desktop/app.go`) получает параметр заголовков.
- 401 → профиль помечается «Требуется вход», серверы остаются до повторного входа.

Клиент OpenWrt не меняется.

## 10. Ошибки

| Ситуация | Ответ |
|---|---|
| Неверный логин или пароль | 401, общий текст |
| Превышены попытки | 429 + `Retry-After` |
| Кабинет выключен | 404 |
| Временный пароль, не смена | 403 `must_change_password` |
| Изменение у выключенного клиента | 403 `client_disabled` |
| Скрыть последний / чужой ключ | 400 с текстом |
| Отозванный токен | 401 |
| Смена пароля LDAP-клиентом | 400 |

## 11. Тестирование

TDD, Go `testing`, настоящая SQLite через `dbtest.InitDB`, `httptest` для HTTP:

- вход по своему паролю; вход через LDAP: проверка каталога вызывается через функцию-поле
  сервиса (по умолчанию `ldap.AuthenticateUser`), в тесте подставляется функция, принимающая
  один логин и пароль; ветка «LDAP выключен» и ветка ошибки каталога проверяются отдельно;
- выключенный клиент получает 403 `client_disabled` на изменения, но может сменить пароль;
- одинаковый ответ на неверный логин и неверный пароль; 429 после лимита;
- временный пароль пропускает только смену пароля;
- смена пароля и «Отозвать доступ» обнуляют токены и веб-сессии;
- скрытая пара исчезает из raw, JSON и Clash; ссылки панели полные;
- правило последнего ключа и отказ на чужой ключ;
- очистка `client_sub_hidden` при удалении хоста, отвязке клиента, удалении клиента и инбаунда;
- `/portal/api/sub` отдаёт тот же вывод, что `/sub/:subid` для того же клиента;
- фронтенд: Vitest для экранов кабинета, `i18n-dead-keys`.
